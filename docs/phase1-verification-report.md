# 阶段一验证报告：回放解析与首次回测

## 结论摘要

回放解析链路完全打通，能从 `.wowsreplay` 完整解出对局元数据与 24 名玩家的战后统计。首次回测暴露出一个决定项目架构的关键事实：**预测所需的特征无法从回放本身获得，只能靠跨对局累积的历史统计**。这印证了中央协调库存在的必要性。

## 验证环境

| 项 | 值 |
|---|---|
| 回放版本 | 15.6.0，build 12830008 |
| 回放来源 | `D:\SteamLibrary\...\replays\15.6.0.0\` |
| 样本量 | 119 份 |
| 解析器 | replayshark v1.0.2 |
| 游戏数据 | landaire/wows-replay-data 的 15.6.0_12830008 |

## 解析能力

成功解出的字段：

- 对局元数据：地图、模式、对局类型、游戏版本、时长、开始时间、胜负。
- 玩家身份：账号 ID、昵称、公会、服务器、组队 ID、是否机器人、是否隐藏战绩。
- 船只信息：船名、舰种、等级、国籍。
- 战后统计：伤害、击杀、点亮伤害、潜在伤害、承受伤害、经验、存活时长。

## 批量解析结果

| 指标 | 数值 |
|---|---|
| 回放总数 | 119 |
| 含完整战斗结果 | 82 |
| 未完成对局 | 37 |
| 胜负分布 | 48 胜、34 负 |
| 平均参战人数 | 23.9 |

未完成的 37 份对局 `played_duration` 为 0 且无 `battle_result`，应跳过入库。这验证了 `ReplaysharkMapper.Map` 中未完成对局返回 null 的处理是必要的。

## 首次回测结果

用基线预测器（双方平均加权胜率差过逻辑函数）对 82 份完整对局回测：

| 指标 | 数值 | 解读 |
|---|---|---|
| Brier 分数 | 0.2500 | 恰好等于无信息基线 |
| 对数损失 | 0.6931 | 恰好等于 ln(2)，即抛硬币 |
| 判别准确率 | 58.54% | 略高于一半 |
| 校准曲线 | 全部落入 0.5-0.6 区间 | 预测值几乎恒定 |

## 关键发现

Brier 0.25 与对数损失 0.6931 是数学上的无信息基线，说明预测器实际输出的概率几乎恒为 0.5。

根因不是算法缺陷，而是**输入缺失**：

回放提供的是战后真实结果，但预测器需要的是赛前就能拿到的历史统计，比如账号总胜率、近期状态、单船表现。回放文件里**不包含**这些信息。因此：

- `PlayerRecord.AccountWinrate` 等字段全部保持 `-1` 哨兵值。
- 队伍聚合时 `withStats` 为空，`AvgWeightedWinrate` 为 0。
- 双方胜率差为 0，逻辑函数输出 `sigmoid(0) = 0.5`。

58.54% 的准确率仅仅来自胜场多于负场（48 对 34），并非模型有效。

## 架构结论

这个发现直接决定了系统架构，与设计文档的三层结构一致：

1. **回放解析层**提供预测的**标签**（真实胜负）与**赛后特征**。它回答"这局打成什么样"。
2. **历史统计层**提供预测的**输入特征**（账号胜率、近期状态、会话状态）。它回答"这些人过去什么水平"。数据来自 WG API 与跨对局累积。
3. **预测层**消费特征、产出概率，其输出与回放标签配对完成校准。

两者必须分离。回放解决标签与闭环，历史统计解决特征。中央协调库的核心价值正在于第 2 层：缓存 WG API 数据、跨对局累积逐场记录，这是近期状态特征的唯一来源。
