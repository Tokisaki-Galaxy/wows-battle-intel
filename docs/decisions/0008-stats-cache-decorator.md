# ADR 0008：战绩缓存做成提供商的装饰器

- 状态：已采纳
- 日期：2026-10-17

## 背景

所有玩家战绩都来自 WG 公开 API，限流严格，重复查询同一批对手是常态：赛前加载界面里 tempArenaInfo 每局重写，同一批对手会在短期内反复出现；历史对局每次选中也重建名单。

最初的缓存写在应用服务 `PlayerStatsService` 里：它既分块推进拉取，又负责查缓存与落库。问题是缓存能力只属于这一个服务，换一个提供商或从别的入口调用就绕过了缓存；CLI 的读取路径就各自直连提供商，没有缓存。

## 决策

把缓存做成 `IPlayerStatsProvider` 的一层装饰器 `CachingPlayerStatsProvider`，包住任意具体提供商。查缓存、TTL 判定、回写都在装饰器里，调用方只依赖接口。

缓存读写抽象成 `IPlayerStatsCache`，由 `SqliteBattleRepository` 实现，按有效期取最新快照，超期视为未命中。

`PlayerStatsService` 退化成薄编排层，只负责"把一大批玩家切成小块逐块推进"，让拉取过程可中断、可增量落库，不再关心缓存细节。

## 理由

**职责单一。** 分块编排与缓存加速是两件事，拆开各自可测。缓存装饰器可以单独用假提供商测，编排层也可以单独测。

**能力可复用。** 装饰器包住接口，任何实现套上都自动获得缓存，CLI 的 live 读取路径与界面同一口径。

**可关闭。** 装饰器用一个开关控制是否读缓存，关闭时每次都联网取最新。写快照不受开关影响，始终落库——快照是训练数据原料，关掉加速不该连带把数据累积关掉。

**TTL 明确。** 原来的快照查询不设新鲜度上界，任何旧快照都算命中，展示层可能长期停在旧值。现在按 TTL 过滤，过期重新联网。

## 代价

**多一层包装。** 一次调用多绕一层。可接受，本项目的提供商种类有限。

**缓存字段扩张。** 让缓存加速路径也能回填公会标签，把 `clan_tag` 放进了 `player_snapshots`。这是身份字段而非统计字段，混进了统计快照表，是有意为之的取舍：一张表一套读写，胜过多开一张只有一列的表。训练侧忽略该列。

## 实现要点

- 命中判据是账号胜率、分舰种、单船三项都齐，与界面补拉口径一致。
- 缓存读失败、超时、无记录一律返回 null，回落网络。
- 开关只控制读缓存，不控制写快照。
- 装饰器只补空值：回放链路已带的公会标签不被缓存覆盖。
- 带公会标签的记录即使没有统计（隐藏战绩）也落一条快照，供跨局回填标签。

## 参考

ADR 0005 的仓储抽象同理：数据访问藏在接口后，业务只依赖接口。本决策把"加速访问"也放在接口后。
