## 真实数据验证

用本机 119 份 15.6.0.0 回放做了完整验证。

解析：119 份全部可解析，82 份含完整战斗结果，37 份为未完成对局被正确跳过。每局解出 24 名玩家的战后统计，入库 1962 条玩家记录。

采集：从这些对局中出现过的 1709 个玩家拉取 WG 公开 API 统计，1608 个成功落盘为快照。

## 关键发现

**时间泄漏是真实约束，防护在正确工作。** 数据库里 82 局有标签，但数据集构造返回 0 条可用样本。原因是战斗发生在 2026 年 7 月，而玩家快照是此刻补采的，时间戳晚于战斗。`dataset.py` 的 `_latest_snapshot_before` 正确拒绝了这些未来信息。

这验证了特征工程文档中"赛前可得"原则的实现是有效的。生产场景下，客户端在开局时采集快照，时间戳自然早于对局，不会有此问题。

**小样本过拟合明显。** 用 `--allow-future` 开关绕过时间检查后，82 个样本配 20 个特征，逻辑回归与 LightGBM 的 Brier 均为 0.3433，反而差于 0.25 的无信息基线。这不是代码缺陷，是样本量与特征数不匹配。

真正的模型精度评估需要积累足量带正确时间戳的数据，这是阶段五后续与中央库采集的目标。

**加权胜率差基线仅微弱优于无信息基线。** Brier 0.2477 对比 0.25，AUC 0.5386。区分度很小，符合预期：赛前可见信息有限，单场结果方差极大。

## 已实现的核心能力

赛前预测链路：回放取名单，WG API 补历史特征，基线预测器输出胜率期望，与真实结果对照，计算 Brier 分数与校准曲线。

数据闭环：回放解析产出标签，统计采集产出特征，本地 SQLite 落盘，`predictions` 表支持事后校准。

中央库骨架：对局众包上报带幂等去重，玩家统计 KV 缓存加 D1 冷备份，模型 R2 分发，服务器基线查询。

模型管线：特征提取与 C# 端口径一致，逻辑回归与 LightGBM 训练，交叉验证，ONNX 导出并经运行时验证一致。

## 待完成

- 真实的赛前预测需要在客户端运行时采集快照，而非事后补采。
- 模型精度需要更多带正确时间戳的数据才能评估。
- 客户端 WPF 界面尚未接入（当前用命令行验证）。
- 边缘后端尚未部署到真实 Cloudflare 账号（绑定 ID 为占位符）。
- 服务器基线计算尚未实现（需要足量快照样本）。

## 架构验证结论

分层设计经受住了真实数据检验。仓储接口抽象让本地 SQLite 与云端 D1 各自实现，回放解析器接口让外部进程实现可替换，特征定义在 C# 与 Python 两端保持一致。时间泄漏防护证明"赛前可得"原则不是空话，而是有代码强制执行的约束。
