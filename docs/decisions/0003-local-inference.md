# ADR 0003：预测在客户端本地推理

- 状态：已采纳
- 日期：2026-10-14

## 背景

模型训练在 Python 端完成，但推理放在哪里有三种选择：客户端本地、服务器端、或两者结合。这决定了延迟、成本、离线可用性、模型更新机制。

## 决策

预测在客户端本地推理，模型文件由服务器下发。

模型导出为 ONNX 格式，放 R2。客户端启动时检查版本，从 R2 拉取最新模型，用 ONNX Runtime 本地推理。服务器只负责补齐本地算不出来的特征，以及下发模型。

## 理由

**延迟最低。** 开局时的预测要即时显示。本地推理没有网络往返。

**不占服务器成本。** 推理是计算密集的，放 Workers 会受 CPU 时间限制，放独立推理服务又要额外成本。本地推理零边际成本。

**离线可用。** 网络波动或中央库不可用时，预测仍能工作。这对游戏内即时性很重要。

**特征大部分本地可得。** 账号统计有本地缓存，近期状态有本地累积的逐场记录。只有新玩家或陌生玩家的历史需要走服务器。

**模型更新简单。** 客户端启动时比对版本号，拉新文件即可。不需要客户端发版。

## 代价

**模型分发有延迟。** 新模型上线后，用户要等到下次启动才生效。可接受，模型迭代频率不高。

**本地算力差异。** 用户机器性能参差。但预测模型很小，一次推理微秒级，不是问题。

**模型保护弱。** 模型文件在客户端，理论上可被提取。对本项目不是问题，模型不是商业机密，开源反而有利于建立信任。

**特征新鲜度。** 本地缓存的玩家统计可能过期，近期状态依赖本地历史，新玩家数据缺失。这部分由服务器兜底。

## 实现要点

- `IPredictor` 接口抽象，`BaselinePredictor` 与未来的 `OnnxPredictor` 各自实现。
- 模型不可用或特征缺失时降级到基线预测器。
- 模型版本与哈希写入每条预测记录，保证可追溯。
- 中央库不可用时，预测降级为本地数据的朴素估计，不阻塞。

## 备选方案

**服务器端推理。** 模型完全可控、能实时更新。代价是延迟、成本、离线不可用，且需要独立推理服务绕开 Workers 的 CPU 限制。

**混合。** 本地为主，陌生玩家走服务器。最稳但最复杂。可作为后续演进方向，但起步阶段不必。
