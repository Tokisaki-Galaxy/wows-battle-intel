## 客户端分层

沿用 ApeRadar 已验证的分层思路，扩展点保持接口抽象。

### 观测层 Observer

职责单一：发现新文件。监听游戏回放目录下的 `tempArenaInfo.json` 与 `.wowsreplay`。观测与解析严格分离，观测层不解析内容，只产出文件路径与时间戳事件。

### 编排层 BattleIntake

一次战斗处理的编排者。串联解析、统计拉取、关注名单、战场计算、预测、持久化。负责重试与取消，持有 `CancellationToken`。

参考 ApeRadar 的 `BattleLoadCoordinator`，它是这个角色的现成范例。

### 解析层 ReplayParser

把回放文件变成结构化的战斗结果。接口 `IReplayParser` 抽象，两个实现：

- `ReplaysharkReplayParser`：调外部 `replayshark dump`，读 JSON lines。零移植成本，版本兼容由 wows-toolkit 维护。近期采用。
- `NodsoftReplayParser`：引用纯 C# 的 `Nodsoft.WoWS-ReplaysUnpack` 库，进程内解析。长期备选。

接口一抽象，切换实现不动上层。

### 统计层 PlayerStats

拉取玩家统计。沿用 ApeRadar 的 `IPlayerStatsAdapter` 模式，实现 Vortex、WG Public、Yuyuko proxy 三个适配器。客户端本地缓存优先，缓存未命中再走网络。

### 预测层 Predictor

输入是双方参战者的特征向量，输出是主队获胜概率与置信信息。本地用 ONNX Runtime 推理，模型文件从 R2 下发。接口 `IPredictor` 抽象，便于测试时替换成固定输出的替身。

### 持久层 LocalStore

SQLite 三张表。写操作与读操作分离，采集写入与校准查询互不阻塞。

### 上报层 Uploader

把本地新增的对局记录匿名化后批量上报中央库。断网时攒在本地，联网后补传。幂等，重复上报不产生重复记录。

## 边缘后端分层

### API 网关

鉴权、限流、路由。按客户端版本与功能分区，避免一次改动影响所有端点。

### 缓存层 KV

玩家统计数据缓存，按账号 ID 键。读多写少，正好匹配 KV 的强项。注意 KV 对同一 key 的写入限制是每秒一次，不要用它存频繁更新的计数。

### 采集入库

回放与对局记录经 Queues 异步入库，削峰，避免客户端上传高峰打爆 D1 写入配额。

### 模型分发

训练好的模型与舰船元数据放 R2，客户端走 R2 直链下载，不占 KV 写配额。R2 出网免费，训练集导出也走它。

### 持久层

起步 D1。所有数据访问藏在 `IBattleRepository` 接口后，将来切 Neon Postgres 时业务代码零改动。

## 关键数据流

### 赛前预测

```text
tempArenaInfo.json 出现
  → 观测层发现
  → 解析出参战者名单
  → 解析服务器
  → 统计层拉取玩家数据（本地缓存优先）
  → 特征工程：账号统计 + 近期状态 + 会话状态 + 服务器归一化 + 组队结构
  → 预测引擎本地推理
  → 输出双方胜率期望
  → 写入 predictions 表（带模型版本与时间戳）
  → 展示
```

### 赛后对照

```text
.wowsreplay 出现
  → 观测层发现
  → 回放解析出真实结果（胜负、每人伤害、击杀、存活、点亮）
  → 写入 battles 与 battle_players 表
  → 关联同一局的 predictions 记录
  → 计算预测误差并展示
  → 累积进校准统计
```

### 数据上报

```text
本地新增记录
  → 匿名化（只保留账号 ID 与统计）
  → 批量打包
  → POST 到中央库
  → Queues 异步入库
  → D1 持久化
  → 失败则保留本地，下次补传
```

## 边界与约束

- 客户端不依赖中央库即可运行。中央库不可用时，预测降级为本地已有数据的朴素估计。
- 中央库不参与实时预测，只提供缓存与模型分发。推理始终在客户端。
- 回放文件默认不上传，只上报匿名化的统计结果。
- 所有时间戳用 UTC 存储，展示时转本地时区。
